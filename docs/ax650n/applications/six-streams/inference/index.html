AX8850 六路推理优化记录

下文 BOARD_IP 为地址占位符，请替换为运行推流程序的开发板 IP。

实测日期：2026-09-16；RK3576 + AX8850 16GB，开发版目录为 ~/ax-pipeline/six。

该版本六路推理合计从 54.0 提升到 58.0 帧/秒（+7.4%）。NPU 平均占用率从 14.4% 提升到 16.0%，提升有限，仍有较多计算余量。

项目源码与新部署说明见 GitHub 仓库；本文中的原部署路径与记录按下述环境使用。

两次测量均播放原有六路视频，开发板 VLC 同时播放本地六宫格。优化前统计窗口约 70 秒，优化后约 130 秒；场景复杂度和取样时段会影响结果。第一路源视频只有 12 FPS，已逐帧处理。

六宫格编码约 30.0 FPS；本次统计窗口各路编码队列丢帧与提交/复用错误均为 0。芯片温度 58–59°C。RK3576 上主程序 CPU 用量从约 247% 降到 209%（单核满载计 100%）。这些是短时性能数据，不作为出货长时间稳定性结论。

本次修改​

  1. 插件使用 Release 优化编译：原构建未启用优化；PCD、YOLO26、YOLOv8 和跟踪相关代码改用 -O3 -DNDEBUG。
  2. 分割只计算保留的掩膜区域：原来每个目标都计算整张 160×160 原型图，再裁掉框外部分。现在先选取同一个区域，再做矩阵乘法。检测、NMS、掩膜阈值和后续缩放保持原有算法。
  3. 深度图只回传有效行：768×768 输出中，本次 16:9 视频使用中间 768×432 区域。每帧回传由 2,359,296 字节降到 1,327,104 字节，减少 43.75%。模型仍以原输入尺寸执行，热力图读取的有效深度值不变。
  4. 推理输出回传增加返回值检查；修正性能统计初始化中的线程竞争，以及对含 C++ 容器对象直接 memset 的问题。

九组掩膜区域对照的数值误差和二值掩膜差异均为 0。小目标掩膜矩阵计算样例从约 1.14 ms 降至 0.083 ms；这是该步骤的微基准，整路帧率见上表。三组深度输出测试的有效行数据逐字节一致。

尝试过合并大块传输、不同分块大小、异步回传和减少同时推理的任务数；它们没有带来合适的整体收益，其中大块传输影响了编码出流，最终部署版已移除这些实验改动。

最终七个 RTSP 地址均可从局域网访问，每路实际解码 30 帧通过；检查了六宫格画面，检测框、分割、深度热力图和计数均有输出，开发板 VLC 本地预览处于播放状态。查看本次六宫格截图。

为什么 NPU 还没有跑满​

当前主机 PCIe 实测为 Gen2 ×1（5 GT/s）。现有模型产生大量浮点输出，例如 YOLOv8s 每帧约 4.84 MB、YOLO26n-Seg 约 7.17 MB，还需要回传到 RK3576 做后处理。采样中模型执行通常只有数毫秒，输出回传与同步等待可达数十毫秒。

进一步大幅提升需要减少模型输出回传，例如把检测解码、NMS、分割后处理放到卡端，或重新转换带紧凑输出的模型，并重新验证结果。这需要增加卡端程序/模型部署工作；单纯增加线程并不能消除当前等待。

使用与回退​

启动和查看帧率：

cd ~/ax-pipeline/six
./start.sh
sudo ./fps.py
sudo /usr/bin/axcl/axcl-smi

开发板 VLC：http://127.0.0.1:8850/overview.ts。

局域网 VLC：rtsp://BOARD_IP:8554/overview。

需要回退时执行：

cd ~/ax-pipeline/six
./rollback-npu.sh

回退脚本恢复本轮修改前的程序、配置和构建脚本，并重新启动服务。备份位于 backups/before-npu-opt-20260916-182855。

原始附件的 source/、bin/ 与 evidence/npu/ 保存对应源码、程序和验证记录，入口见项目资料。板端构建脚本 build.sh 会重编优化插件并生成程序，依赖板端原有 ax-pipeline 源码和 SDK 构建目录；这些文件不是独立安装包。
