# 测量帧率与资源

在默认演示稳定运行后记录性能。比较两次结果时保持输入、模型、运行程序、播放器连接数和采样时长一致。

## 读取实际处理帧率

```bash
cd ~/ax8850-multistream-demo
python3 tools/fps.py
```

脚本读取 `ax8850-multistream` 当前启动实例的日志，按累计计数差和实际时间计算速率。至少需要两次统计，启动后约 30 秒再执行；运行足够久时通常覆盖约 60 秒窗口。旧实例日志不会混入本次结果。

| 指标 | 含义 | 观察重点 |
|---|---|---|
| Decode | 解码帧率 | 输入能否持续解码 |
| New video | 新画面更新帧率 | 实际更新是否跟上源视频 |
| AI | 模型推理帧率 | 标注更新速度，与视频帧率不同 |
| Encode | 单路编码帧率 | 输出码流是否连续 |
| Drops | 渲染队列替换与编码队列丢帧之和 | 在采样窗口内是否增长 |
| Errors | 封装与提交错误之和 | 是否有运行错误 |
| Overview encoder | 六宫格编码帧率 | 总览输出速度 |

总览编码使用 30 FPS，不表示每格新增 30 帧或每个模型推理 30 次。容器或 RTSP 元数据中的帧率也可能取整，判断实际速度应以计数采样和画面更新共同确认。

## 观察主机与算力卡

```bash
axcl-smi
free -h
df -h .
ps -C six_app -o pid,%cpu,%mem,etime,args
```

记录算力卡温度、CMM 占用、NPU 利用率，以及主机 CPU、内存和磁盘余量。`axcl-smi` 显示瞬时状态，不能将某一时刻占用当作峰值。录像会持续占用磁盘；开发板本地 VLC 也会消耗主机解码资源。

建议先在电脑观看 RTSP，取得基础采样，再添加本地桌面播放并比较两组结果。若温度持续上升或处理计数停止，停止负载并检查散热与运行日志。

## 理解性能变化

视频处理、模型推理和输出编码并行进行。推理速度低于视频更新速度时，应用使用最近的 AI 结果绘制标注；提高输出帧率本身不会提高模型推理帧率。

改变模型、视频尺寸、视频帧率或后处理策略后，重新采样六路数据，并检查快速运动时的标注滞后。仅提升编码帧率而未改善画面更新和推理速度，不能视为整体性能提升。

仓库参考结果与测试边界见[效果与验收](validation.md)。

## 使用与回退

性能调整先保留配置，按[更换视频与配置](frame-rate.md)执行；异常时恢复备份并重新启动。修改程序则重新执行 `bash build.sh`，确认使用的是 `build/install` 产物后再比较，不要将预编译与构建版本的结果混在一起。
